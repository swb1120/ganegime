# 계산 조건을 바꿨을 때의 결과

2026.11.13, release 0.6.3의 클라우드 계산기를 그대로 호출했습니다. 가상 입력을 이용한 민감도 분석이며 사용자 실험이나 상용 내비 성능 비교가 아닙니다.

## 재실행

소스 ZIP의 `ganegime/`에서 Node.js로 실행합니다. 외부 API, 접속 코드, 추가 패키지는 필요 없습니다.

```text
node evidence/benchmark.mjs evidence/results
```

`cloud/planner.mjs`의 SHA-256을 결과에 기록합니다. 원본 제출 APK와 서버 코드는 변경하지 않았습니다. 보고서는 계산 동작의 설명을 보강하기 위한 추가 자료입니다.

## 입력을 정한 방법

영상의 세탁, 택배, 장보기 예제에서 사용하는 고정 이동시간 표를 사용합니다. 아래 값의 모든 조합 108개를 계산하고 불리한 결과도 포함했습니다. 서로 다른 도로 108곳이나 사용자 108명이 아닙니다. 별도 사전등록 연구는 아니며 결과 수를 확인한 뒤 입력 범위를 조정하지 않았습니다.

| 조건 | 사용한 값 |
|---|---|
| 18:00 기준 출발 지연 | 0, 5, 10, 20분 |
| 택배 완료 마감 | 18:25, 18:40, 19:00 |
| 장보기 처리시간 | 20, 30, 40분 |
| 귀가 목표 | 19:20, 19:35, 19:50 |

세탁은 5분, 19:00 마감, 필수, 택배는 10분, 선택, 장보기는 필수, 마지막 방문 선호입니다. 출발은 회사, 목적지는 집입니다. 이동시간 표와 실행 결과는 `results/summary.json`과 `results/scenarios.json`에 모두 포함했습니다. 거리는 평가하지 않아 matrix의 meters는 0입니다.

기준 계산은 같은 볼일 3개를 전부 방문하면서 이동시간만 최소화합니다. 추천은 완료 마감, 귀가 목표, 방문 선호를 포함한 기존 계산기를 사용합니다. 각 조건에서 6개 순서를 비교합니다. 모든 볼일의 완료 마감과 최종 귀가 목표를 지켜야 전체 완료로 셉니다. 선택 볼일을 빼는 대안은 별도로 셉니다.

## 결과

| 결과 | 조건 수 |
|---|---:|
| 두 방식 모두 전체 완료 가능 | 34 |
| 추천에서만 전체 완료 가능 | 10 |
| 두 방식 모두 불가능 | 64 |
| 합계 | 108 |

추천의 전체 완료 가능 조건은 44개, 이동시간 최소 기준은 34개입니다. 추가 이동시간은 최대 2분입니다. 64개의 불가능한 조건 중 55개는 선택 볼일인 택배를 미루는 대안이 있습니다. 나머지 9개는 이 대안도 없습니다. 필수 세탁, 장보기는 어떤 대안에서도 제외하지 않았습니다.

## 실패할 수 있는 조건

추천 순서를 고정한 채 매장마다 처리시간이 5분씩 더 걸린다고 가정하면, 원래 가능했던 44개 중 34개는 마감 또는 귀가 목표를 놓칩니다. 이 실험에서는 추가 지연 후 재계산하지 않았습니다. 주차, 대기를 처리시간에 포함하고 실제 오차를 측정해야 한다는 점을 보여줍니다. 시간을 보장하거나 미래 교통을 예측하는 기능은 아닙니다.

조건이 느슨하면 최단 이동 순서도 충분하고, 너무 촉박하면 순서를 바꿔도 해결되지 않습니다. 특정 예제에서 이동 2분을 더 쓰는 것이 실제 운전자 전체에게 유리하다는 결론은 낼 수 없습니다.

## 검산과 한계

반환된 도착, 완료시각, 이동시간 합, 전체 완료 여부를 production `evaluate`를 호출하지 않는 별도 산술 코드로 검산합니다. 필수 볼일을 유지하는지도 확인합니다. 다만 동일 개발자가 작성한 검산이며 독립 기관 검증을 뜻하지 않습니다.

고정된 하나의 대칭 이동시간 표, 일정한 처리시간, 3개의 볼일만 사용했습니다. 비대칭 도로, 실시간 혼잡 변화, 주차 가능 여부, 매장 영업과 실제 처리시간 분포를 대표하지 않습니다. 이 결과로 사용자 수, 유지율, 실제 절감시간, 수상 가능성을 추정하지 않습니다.
